# TPS Notebook Navigator 9.1.0 — Discover properties and rename values

This additive minor release removes the configured-key whitelist from Properties navigation and adds a confirmed bulk value rename. Minimum Obsidian remains **1.11.0**. Tested and deployed only in **Obsidian Plugin Test Vault**; ready for the user's BRAT pull. Production was not accessed or updated.

## Behavior

- Every top-level frontmatter key in the existing visible-note index is discoverable without adding it to GCM or Navigator configuration. Blank, numeric, boolean and object-valued keys are retained. Existing configured empty placeholders remain. Object members are not flattened into new dotted keys; Obsidian's synthetic position metadata is excluded.
- Explicit per-profile navigation hides and existing note/folder exclusions remain authoritative. List pills and file-menu visibility remain separate opt-ins. Standalone configuration and the shared GCM visibility API agree that unconfigured keys are visible in navigation; explicitly hiding one remains persisted.
- Right-click or long-press a value and select **Rename value…**. The existing modal selects the current value, previews affected notes across the vault, including hidden notes, and allows exact-only or nested-value replacement. Nested renames keep child suffixes and do not match similar prefixes such as `oldish`.
- Preserve scalar/list shapes, numbers and booleans, unrelated properties and note bodies. Merge only list collisions introduced by the rename. Invalid typed targets or unavailable metadata abort before writing. The current source is rechecked inside Obsidian's atomic frontmatter callback. Removed, changed or failed notes are reported without retry or repair.
- This changes note frontmatter values only. Templates, Base queries, plugin classifier/status settings and shortcut targets are not rewritten. Link values are complete frontmatter replacements using the tree's matching semantics; linked notes are not renamed.
- No new background service, poller, cache, startup writer, body scan, persistent settings field or migration is added. Existing metadata/index refreshes handle actual edits. Necessary list grouping remains independent of sidebar visibility.

## UI and configuration contract

No settings destination or disclosure is added. The existing property rename modal is reused with native text input, checkbox and buttons, selected initial text, and duplicate-submit prevention. Existing wrapping/mobile styles remain. New copy is English in untranslated locale entries. Physical iPhone interaction has not been verified.

Opening configuration or a rename preview does not save notes or call providers. No automatic per-key configuration migration is performed. Existing saved preferences remain; a normal version acknowledgement changes `lastShownVersion`.

Covers discovery with no catalog, new-key events, explicit hides, all-off persistence, metadata preservation, exact/nested/list/typed changes, introduced collisions, unknown metadata, concurrent edits, deletion and write failure.
- Full ESLint: zero errors, 26 existing warnings. Final touched grouping files also pass scoped ESLint. Style lint, namespace, artifact/operational identity, TypeScript, string usage and locale-shape gates pass. Separate final production-mode build deploys only byte-changed artifacts to the test vault.
- A 1,000-note fixture makes exactly three matching frontmatter-writer calls, zero body reads and zero settings saves. Repeating the rename adds zero writer calls. A new unconfigured-key event schedules one existing tree rebuild; 100 unchanged events add no rebuilds, inventories or body reads. Host/filesystem behavior is mocked in these owner-level counts.
- Targeted unload, manifest refresh and reload verify installed **9.1.0**. Source, runtime and release artifact hashes are checked independently.
- Foreground native UI: an unconfigured key appears with its nested values; exact-only preview changes from three files to two. Exact rename changes two notes, merges an introduced list collision, and leaves the nested note unchanged. Renaming a synthetic parent changes `old/child` to `record/child`, preserving `oldish/child`. Four original bodies, IDs and unrelated blank/numeric/object properties remain intact.
- Opening the preview makes one metadata inventory, zero body reads and zero writer calls. The exact and nested commits enter the frontmatter writer for two and one matching files respectively. Final-bundle native confirmation changes three matching notes with exactly three frontmatter/process calls. Ordinary changed-file indexing remains; no full-vault body scan is observed. The three-note explicit batch observation includes one 135 ms long task; bulk mutation is not claimed to be latency-free.
- A native **New note** action on an unconfigured value creates one plain note in the temporarily selected Inbox QA folder, with exactly the selected scalar key/value and no injected task kind/status. Default creation location is restored. Task-specific creation defaults are unchanged and were not separately modified for this release.
- A final metadata audit finds all **262** authored top-level keys in the existing property tree, zero missing keys and zero unavailable metadata caches. The tree contains 272 keys including retained configured placeholders. This is a test-vault audit, not production inventory.

- QA notes are archived directly under `_archive`; temporary core creation settings, diagnostic wrappers and event listeners are restored/removed. Original note/Reading view and root/archive presentation are restored. No outbound automation was enabled.

## Scope and rollback

Bulk rename is a sequence of per-note atomic edits, not a cross-vault transaction. The metadata inventory defines candidates; concurrent new matches can fall outside a running batch. Source edits are preserved and partial failures are reported. There is no new repair, retry or automatic undo system.

Downgrading to 9.0.0 restores its configured-key whitelist and removes the new action. It does **not** undo explicitly renamed note values. Existing settings/state are retained. Prior retired integrations and maintenance remain retired.
